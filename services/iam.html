IAM — Identity and Access Management

Manage access to AWS services and resources securely. Control who is authenticated and authorized to use resources through users, groups, roles, and policies.

Security Domain Global Service Free

Introduction

AWS Identity and Access Management (IAM) is a web service that helps you securely control access to AWS resources. IAM allows you to manage users, security credentials, and permissions to determine which AWS services and resources users can access.

IAM is a global service — it is not tied to any specific AWS region. IAM identities (users, groups, roles) and policies are available across all regions.

IAM is provided at no additional charge. You are charged only for the AWS resources that your IAM users consume.

Why do we need IAM?

When you create an AWS account, you start with a single sign-in identity called the root user. The root user has complete access to all AWS services and resources in the account — including billing and account closure.

Using the root user for everyday tasks is a significant security risk. IAM exists to solve this:

  • ✓ Create individual users with specific permissions (least privilege)
  • ✓ Grant temporary access to resources without sharing long-term credentials
  • ✓ Control who can access what, from where, and under which conditions
  • ✓ Enable multi-factor authentication (MFA) for additional security
  • ✓ Audit and track access with CloudTrail

Core Concepts

IAM Users

An IAM user is an identity representing a person or application. Users have permanent long-term credentials (passwords and access keys). Best practice: create one IAM user per person — do not share credentials.

IAM Groups

An IAM group is a collection of IAM users. Groups let you assign permissions to multiple users at once. Users can belong to multiple groups. Groups cannot contain other groups — they are flat (one level only).

IAM Roles

An IAM role is an identity with permissions that can be assumed temporarily by users, services, or applications. Unlike users, roles do not have permanent credentials. They generate temporary security tokens via STS.

Roles are used when:

  • An EC2 instance needs to access S3 (attach an instance profile)
  • A Lambda function needs to write to DynamoDB
  • Cross-account access is required
  • Federated identity (SAML, OIDC, Cognito) needs AWS access

IAM Policies

An IAM policy is a JSON document that defines permissions. Policies specify what actions are allowed or denied on which resources and under which conditions.

Example IAM Policy — Read-only access to a specific S3 bucket
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ]
    }
  ]
}

Policy Types

AWS Managed Policies

Predefined by AWS. Examples: AdministratorAccess, ReadOnlyAccess, AmazonS3FullAccess. Maintained and updated by AWS.

Customer Managed Policies

Created and managed by you in your AWS account. Reusable and can be attached to multiple identities.

Inline Policies

Embedded directly in a single user, group, or role. Deleted when the identity is deleted. Not reusable.

Service Control Policies (SCPs)

Used with AWS Organizations to restrict the maximum permissions available in member accounts.

Policy Evaluation Logic

IAM uses an explicit deny-by-default model. When evaluating whether a principal can perform an action, AWS follows this order:

  1. 1. Is there an explicit Deny? → DENY (always wins)
  2. 2. Is there an explicit Allow? → ALLOW
  3. 3. Default: → IMPLICIT DENY

MFA (Multi-Factor Authentication)

MFA adds an extra layer of protection on top of username and password. AWS supports Virtual MFA (Google Authenticator, Authy), U2F hardware keys (YubiKey), and hardware MFA devices.

Best practice: Enable MFA on the root account and all IAM users with console access. Use IAM conditions to require MFA for sensitive actions.

Access Keys

Access keys (Access Key ID + Secret Access Key) are used for programmatic access to AWS (CLI, SDK). Key rules to remember:

  • Each IAM user can have a maximum of 2 access keys
  • Access keys are only visible once at creation — rotate them regularly
  • Never commit access keys to source code or store in public repositories
  • For EC2/Lambda, use IAM roles — not access keys

Real-world Use Cases

🏢
Team access management
Create groups for Dev, QA, and Ops. Assign policies to groups so each team gets the access they need — nothing more.
🤖
EC2 accessing S3
Attach an IAM role with S3 permissions to an EC2 instance profile. The app can access S3 without hardcoding credentials.
🔄
Cross-account access
A developer in Account A assumes a role in Account B to access resources. Enables central logging, security, or deployment accounts.
🌐
Federated identity (SSO)
Allow corporate Active Directory users to sign in to AWS via SAML federation without creating individual IAM users.
📱
Mobile app access (Cognito)
Use Cognito Identity Pools to grant mobile app users temporary IAM credentials to directly access AWS resources like S3 or DynamoDB.
🔐
CI/CD pipeline permissions
Grant a GitHub Actions workflow a role (via OIDC) to deploy to AWS without storing access keys as secrets.

Best Practices

🔒
Lock down the root account
Enable MFA on root. Create an IAM admin user for daily use. Do not create access keys for root. Store root credentials in a password manager.
📏
Apply the principle of least privilege
Grant only the permissions needed to perform a task. Start with minimal permissions and add more as needed. Use IAM Access Analyzer to identify over-permissive policies.
👥
Use groups to manage permissions
Never attach policies directly to individual users. Assign users to groups and attach policies to groups. Makes permission management much easier at scale.
🔑
Use roles, not access keys
For AWS services (EC2, Lambda, ECS), always use IAM roles. For CI/CD, use OIDC-based role assumption. Rotate access keys regularly and audit unused ones with the IAM credential report.
📋
Set a strong password policy
Configure an account-wide IAM password policy: minimum length, complexity requirements, rotation period, and prevent password reuse.

Exam Tips — SAA-C03

💡 IAM is global
IAM users, groups, roles and policies are global — not region-specific. This comes up in questions about cross-region access.
💡 Explicit Deny always wins
If a policy has an explicit Deny for an action, it overrides any Allow — regardless of how many other policies grant it. This is the most tested IAM concept.
💡 Roles for AWS services, not access keys
Any question asking "how should an EC2 instance securely access S3?" — the answer is an IAM role attached as an instance profile. Never hardcoded credentials.
💡 Groups cannot contain groups
IAM groups are flat — you cannot nest a group inside another group. Users belong to groups; groups cannot have sub-groups.
💡 STS & AssumeRole for cross-account
Cross-account access scenarios always involve IAM roles and sts:AssumeRole. A trust policy on the target account's role must explicitly allow the source account/principal.
💡 Know the credential report & Access Advisor
The IAM Credential Report lists all users and their credential status. Access Advisor shows which services a user has accessed, helping identify unused permissions.
